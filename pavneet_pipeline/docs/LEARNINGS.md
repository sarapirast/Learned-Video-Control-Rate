# Learnings

- **Cluster:** session node had 2 CPU / 8 GB only. `main` is usually full; `oneweek` (7-day limit) often has idle 64-core/256 GB nodes (`d05`, `d11`, `d18`). No x265/x264/ffmpeg on PATH by default; `ffmpeg/7.1.1` and `conda/25.11.0` modules exist.
- **Runbook errors so far:** `/scratch` -> `/scratch1`; assumes code is shipped alongside (it isn't); "12 pilot clips from GitHub" have no stated source.
- **`/scratch1` is Lustre (`lfs1`)**, not BeeGFS as the cluster notes say. `du` on a just-written file reports ~1 KB (size shows up later); use `stat -c %s` / `ls -l` for sizes.
- **conda-forge `ffmpeg` pulls in x265 3.5 and x264 0.164 binaries** into the env's `bin/`. Our x265 4.1 / x264 builds go into a separate prefix `/scratch1/pbanga/envs/codecs` that comes first on PATH.
- **x265 4.1 does not configure with CMake 4.x** (removed `cmake_policy(... OLD)` support); built with the system `/usr/bin/cmake` instead.
- Package versions installed (latest on PyPI/conda-forge on 2026-10-29, Python 3.12): numpy 2.5.4, scipy 1.18.1, pandas 3.1.0, gymnasium 1.4.0, stable-baselines3 2.9.2, sb3-contrib 2.9.2, scikit-learn 1.9.1, matplotlib 3.11.2, opencv-headless 5.0. These match the runbook's pins except SB3 2.9.2 (runbook 2.9.0) and Python 3.12 (runbook 3.14).
- **L3 — x264 ignores qpfile QPs under `--qp`** (CQP mode keeps its own I/P constants). Under `--crf` with `--aq-mode 0 --no-mbtree`, qpfile QPs are obeyed exactly (checked per frame with `--verbose`). x265 obeys qpfile under `--qp`. So forced encodes use `--qp` (x265) / `--crf` (x264) as carrier mode. The runbook only says "AQ and cutree off"; it would have silently produced wrong x264 results.
- **x265 per-frame CSV bits = NAL payload without start codes and without VPS/SPS/PPS.** Our bitstream count (payload, param sets included) equals the CSV exactly on P frames; the I frame is +552 bits (parameter sets).
- **ffmpeg `psnr` filter pairs frames by timestamp**: raw yuv input (25 fps default) vs a 30 fps bitstream misaligns frames; normalise with `setpts=N/(30*TB)` on both inputs. Our numpy Y-PSNR then agrees with ffmpeg to < 0.005 dB.
- **Speed (fast preset, 320x180, 30 frames, 1 thread, incl. ffmpeg decode + PSNR):** x265 ≈ 0.32 s, x264 ≈ 0.20 s per GOP encode; first pass (ultrafast, no decode) 0.12 s / 0.05 s. Similar to the runbook's "x264 ≈ 1.5x faster".
- **Encoders' own RC on one 30-frame GOP (foreman, budget = own CQP 30):** single-pass ABR undershoots a lot (x265 −8 %, x264 −15 %, with AQ −20 % / −35 %); 2-pass is within ~1 % (x265) / 3–9 % (x264); ABR+VBV(1 GOP buffer) lands +2…+5 %. Single-pass ABR has no time to converge in 30 frames — a relevant baseline caveat.
- **STATIC can overshoot badly on static content at QP 30:** STATIC's I frame is 6 QP below base, the encoders' own `--qp` I frame only ≈ 3 below (ipratio 1.4). When the I frame dominates a GOP's bits, STATIC lands ~30–40 % over budget (penalised score down to −60 on such GOPs). The search's gain there is mostly removing overshoot. Watch whether this dominates mean scores; report medians and over-rate alongside means.
- **Job-submission limits:** QOS `normal` (partition `main`): 100 running jobs, 5000 submitted, 2000 CPUs per user. Partition `oneweek` has its own QOS: **50 submitted jobs, 208 CPUs per user** — and a job submitted to `main,oneweek` counts against it, so big arrays must go to `main` only.
- **Batch jobs need `module load gcc/13.3.0` after `module purge`:** x265 (C++) was compiled with it and needs its libstdc++ (`GLIBCXX_3.4.32`); the first x265 infos array failed on every GOP for this. x264 (C) was unaffected.
- **First real results (x264, 2026-10-29 ~01:30):** fitted scene detector (hist 0.2, msad 2.0, fp 1.8) reaches **F1 0.958 on test splices** (precision 0.948, recall 0.968); histogram change alone gets 0.948, motion-compensated SAD 0.679, first-pass-bits spikes 0.495 — the colour histogram carries almost all of it, the others mainly trade recall for false alarms. Natural GOPs with a detected cut: films 16–20 %, UGC 8.5 %, Xiph HD 5 %, Xiph CIF 0.4 %.
- **STATIC in x264 saves only ~1–2.5 % vs constant QP but is over budget on ~50 % (QP 30) and ~70 % (QP 38) of GOPs** — the budget penalty will dominate unless the controller learns to stay within budget. Over-rate is a first-class result, not a footnote.
- **x264 2-pass fails outright at very low targets** (`--bitrate 3`, a near-black GOP at the start of Sintel): own-RC encodes are now allowed to fail per GOP and are counted as "encoder failed" in the reports instead of killing the shard.
- **One RL run hung silently** (x264 cql_ppo k1 s1: no output for 6.9 h after the dataset was built, i.e. in CQL training or PPO env start-up — most likely a forkserver/SubprocVecEnv start-up deadlock). The 12 h array time limit would have let it burn the full slot; retries now use a 2 h cap. Consider a per-run watchdog if it recurs.
- **x265 own-RC is not broken, the metric is harsh (2026-10-29):** 2-pass lands at median 0.99 (QP30) / 1.02 (QP38) of the target; "over %" counts *any* excess, so ~50 % of GOPs are "over" by 1–3 %. Most of its negative score is PSNR loss from the default `qcomp 0.6` (8-GOP probe: qcomp=1 improved saving, worst GOP −31 % → −10 %). Integer-kbps rounding adds up to ±7 % target error on 17 % of QP38 GOPs (our artifact). Candidate extra baseline: own RC with `--qcomp 1` (PSNR-tuned).
- **x264 ABR collapses at very low budgets:** up to 127/958 test points land below x265's QP50 PSNR (outside the common yardstick).
- **Bad nodes (2026-10-29):** d11-41 and d11-22 killed 3 RL tasks with SIGBUS (exit 135) during start-up, no output, 4–8 min in; tasks on 25+ other nodes fine. Likely BeeGFS mmap failures on those nodes. Excluded via --exclude / scontrol ExcNodeList; worth reporting to CARC.
- **analysis.py merged the fb/sum feature runs into plain CQL->PPO (fixed 2026-10-31).** Its configuration key had no `extra` field. The lookahead report's k=5 and k=29 rows therefore averaged 9 runs labelled "3 seeds" (x265 k=5 showed 3.20 instead of 3.48, k=29 3.02 instead of 2.37). `pick()` now keeps `extra` runs apart by default. Reports for both encoders were regenerated. breakdown.py was never affected because it builds its labels from the run arguments.
- **Multi-GOP metric:** averaging PSNR in dB across GOPs gave the hindsight plan a +36 % "saving" by putting bits into cheap static GOPs; MSE pooling is used instead (D25).
- **Model-based PPO exploits the model:** in-model score rose to 9.7 within 25 k steps, then diverged (−inf saving → NaN logits). Fixed by bounding the PSNR delta and the score (D26); results pending.
