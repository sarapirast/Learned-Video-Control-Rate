# Running the project from scratch on an HPC node, in x265 and x264

This runbook is written for a Claude Code session (or a person) on a Linux HPC server that has this project's code but
no data and no results. It is a fresh, independent run: every clip is downloaded and prepared, every search, model and
evaluation is computed on the server, and every report is written new. No earlier results are provided or needed; the
analysis is to be done from what this run produces.

The whole pipeline runs **twice, once per encoder**: x265 (HEVC) and x264 (H.264). Each run is complete on its own
(its own constant-QP curves, budgets, hindsight search, RL training, validation choices and its own rate control as a
baseline). At the end, `experiments/codecs.py` puts the two side by side in `results/codecs_report.md`.

Final outputs:
- `results/expand2_report.md` in each run's folder: lookahead curve k = 0..10 + full GOP, the share of the hindsight
  search's gain each k captures, and the encoder's own rate control on the same budgets.
- `results/codecs_report.md`: both encoders in one table, scored against each encoder's own constant QP and against a
  common yardstick (x265 constant QP).

Section 9 says how to scale the runs up once the baseline runs have finished.

---

## 0. Ground rules for the Claude running this

- **Never ask for, type, or store the user's password.** Log-in is by SSH key only. If anything prompts for a
  password (sudo, git, a web login), stop and ask the user to do that step themselves.
- **Downloads:** the pipeline fetches about 40 GB of public test video (Xiph, Blender films, YouTube UGC). The user
  approved these sources for this project, but confirm with the user once before starting the fetch scripts on a new
  machine. The x264 run reuses the x265 run's downloads (section 7); nothing is downloaded twice.
- **Run the method exactly as written first.** Budgets, the metric, splits, seeds, step counts and the STATIC
  pattern stay as they are for the baseline runs. Scale-ups (section 9) go into separate work directories afterwards.
- **Everything is resumable.** Each script caches every finished stage as a `.pkl` (or model `.zip`) under
  `$RC_WORK/results_<name>/` and skips it on the next run. If a job dies or hits its wall time, resubmit the same
  command. To redo a stage, delete only its `.pkl`.
- Run `--quick` first for every script (minutes, writes to `results_<name>_quick/`), then the full run. A script's
  `--quick` mode reads the full results of the scripts before it, so do quick then full one script at a time.
- Log every run to `$RC_WORK/<name>.log`, and after each script finishes run its `--report`.

## 1. What the run computes (one paragraph)

Per-frame QP rate control in a real encoder under a per-GOP bit budget. An episode is one 30-frame GOP (IDR + 29 P
frames) at 320x180. The agent picks each frame's QP as an offset on a fixed spend-early pattern (STATIC = −6, −3, +3;
the same pattern and action space in both encoders). The budget is the bits the encoder's own constant-QP mode spends on
that GOP at QP 30 or 38. The score is the % of bits saved at equal PSNR versus that constant QP (log-bits interpolation
over QP 18–50), with GOPs over budget penalized. A 300-encode hindsight hill-climb per GOP is the teacher and the
ceiling. Policies: CQL on all logged search plans, then PPO fine-tuning with a relative reward, 3 seeds, at lookahead k
frames. Bits are the real bitstream size (x265's per-frame CSV; for x264 the size of each frame's NAL units); PSNR comes
from decoding the real output with ffmpeg. Code: `rclib/hm265.py` (encoder harness; `RC_CODEC` picks the encoder),
`rclib/env265.py` (Gym env), `rclib/offrl.py` (offline RL), `experiments/*.py` (one file per study).

## 2. Get the code onto the server

The project is not a git repository. From the laptop (WSL), copy the folder to the server with rsync over your SSH
key, e.g.:

```bash
rsync -av --exclude '__pycache__' --exclude 'results/' \
  "/mnt/c/Users/pavne/OneDrive/ドキュメント/599project/" <user>@<hpc-host>:~/599project/
ssh <user>@<hpc-host> mkdir -p 599project/results
```

Copied: `rclib/`, `experiments/`, `tools/`, `data/` (2 MB of cached pilot tables that `tools/smoke_test.py` uses),
`setup_wsl.sh`, `PLAN.md`, this file. Not copied: `results/` (the laptop's reports; the server writes its own, and the
clip-window files `results/expand_clips.json` and `results/expand2_clips.json` are regenerated by the `--prep` steps).
Do not copy the laptop's `~/rcwork` either: nothing from earlier runs is reused.

## 4. Settings for the node (environment variables, no code edits)

| Variable | Meaning | Value |
|---|---|---|
| `RC_CODEC` | encoder for every encode in the pipeline | `x265` (default) or `x264` |
| `RC_WORK` | work directory: clips, GOP cache, every result | on scratch, one per encoder, e.g. `/scratch/$USER/rcwork` and `/scratch/$USER/rcwork_x264` |
| `RC_WORKERS` | processes for independent encodes (searches, evaluations) | cores − 2 |
| `RC_ENVS` | parallel PPO environments | **leave at 14** for the baseline runs |

Why `RC_ENVS` is separate: PPO collects `n_steps = 64` per environment, so its batch per update is 64 × RC_ENVS.
Changing it changes the training recipe. `RC_WORKERS` only changes speed. (`static_pattern.py` takes `--workers`.)

Disk: the x265 work directory needs ≈ 60 GB (45 GB data + download temp space); the x264 one ≈ 15 GB, because it
links to the x265 run's downloads (section 7).

Memory: each worker is one single-threaded encode plus a little numpy. The largest peak is building the CQL dataset for
k = 29 in `expand2.py` (its observation rows are 2.4× wider than k = 5's), which is why `LOG_CAP = {29: 24}` exists on
the 15 GB laptop. Request ≥ 64 GB per job; with more, LOG_CAP can be removed (section 9).

Run Python with `python -W ignore` and filter SB3 chatter: `2>&1 | grep --line-buffered -v -i -E 'warning|batch_size|n_steps='`.

## 5. The pipeline, in order (the x265 run)

Later scripts load earlier scripts' cache files, so the order matters. Run from the project folder with
`RC_CODEC=x265` (or unset) and `RC_WORK=/scratch/$USER/rcwork`. Times are approximate laptop times at 14 workers;
on a 64-core node the encode-bound stages are several times faster.

| # | Command | Makes | Needs | Laptop time (approx.) |
|---|---|---|---|---|
| 1 | `python tools/prepare_clips.py` | 12 pilot clips + `spliced1-3` in `$RC_WORK/clips` (downloads ≈ 100 MB from GitHub) | – | minutes |
| 2 | `python -c "import sys; sys.path[:0]=['rclib','experiments']; import rl_suggestions as S; S.make_test_splices()"` | `spliced4-5` (test splices built only from test clips) | 1 | seconds |
| 3 | `python experiments/static_pattern.py --workers $RC_WORKERS` | fits the best fixed pattern on training clips; report only (STATIC is hard-coded) | 1 | 0.5 h |
| 4 | `python experiments/rl_suggestions.py` | `results_rl/` (BC→PPO, first k sweep). Optional: `rl_matrix` reuses its infos/test search if present, else recomputes them | 2 | 1–2 h |
| 5 | `python experiments/rl_matrix.py` | `results_matrix/`: infos, **training searches** (`search_train.pkl`), every learner, seed-0 models. Builds `spliced6-9` | 2 | ≈ 15 h |
| 6 | `python experiments/seeds.py` | `results_seeds/`: seeds 1–2 of the top configurations | 5 | ≈ 3 h |
| 7 | `python experiments/switch.py` | `results_switch/`: causal rule + GOP-level switch | 5, 6 | 0.5 h |
| 8 | `python experiments/overshoot.py` | `results_overshoot/` | 5–7 | 1 h |
| 9 | `python experiments/lagr.py` | `results_lagr/`: Lagrangian fine-tunes (`lagr_rel_k0_s*.zip`) | 5–8 | 1–2 h |
| 10 | `python experiments/cutspec.py` | `results_cutspec/` (cut-specialist; optional, report only) | 5–7 | 1 h |
| 11a | `bash tools/fetch_xiph.sh` | `$RC_WORK/src`: Xiph CIF/720p clips + BBB, Elephants Dream, Sintel trailer (≈ 13 GB after unpacking) | – | network |
| 11b | `python experiments/expand.py --prep` | film windows + new clips in `clips/`, `results/expand_clips.json` | 11a | 10 min |
| 11c | `python experiments/expand.py` | `results_expand/`: searches on new train clips, CQL→PPO k ∈ {0,2,29,5}, Lagrangian, rules | 5–9, 11b | ≈ 16 h |
| 12 | `python experiments/extend.py` | `results_extend/`: the encoder's own rate control, MPC, gate, BC/A2C/DQN, features, PID Lagrangian (`lagr_pid_k5_s*.zip`), k=1,10 | 11c | ≈ 20 h |
| 13a | `bash tools/fetch_more.sh` | `$RC_WORK/more`: Tears of Steel, Sintel full film, 9 Xiph HD, 87 YouTube UGC 360P clips (≈ 25 GB transferred, 7.2 GB kept) | – | network, 1–3 h |
| 13b | `python experiments/expand2.py --prep` | BBB windows not overlapping step 11, Sintel/ToS windows, UGC split; `results/expand2_clips.json` | 11b, 13a | 10 min |
| 13c | `python experiments/expand2.py` | `results_expand2/`: training searches on the new data, rules, previous-data policies, **test-set hindsight search**, **the encoder's own rate control**, **CQL→PPO for k = 5, 10, 0, 3, 7, 1, 2, 4, 6, 8, 9, 29** (3 seeds each), PID Lagrangian | 11c, 12, 13b | ≈ 35 h |

After each script: `python experiments/<name>.py --report` writes `results/<name>_report.md`
(`rl_matrix_report.md`, `seeds_report.md`, `switch_report.md`, `overshoot_report.md`, `lagr_report.md`,
`cutspec_report.md`, `expand_report.md`, `extend_report.md`, `expand2_report.md`).

Sizes to expect in `$RC_WORK`: `src` 13 GB, `films` 2.6 GB, `clips` 4 GB, `gops` 4 GB (one raw file per GOP, made on
first use), `more` 7.2 GB, results ≈ 150 MB.

### Where the time goes
- **Hindsight search:** 300 encodes × 2 seeds × 3 QPs per training GOP (≈ 38 s per GOP at 14 workers on the laptop),
  and 300 × 2 × 2 per test GOP in `expand2.py`. Scales linearly with cores.
- **`infos`** (first-pass features + the constant-QP curve over QP 18–50 for every GOP): 33 encodes per GOP.
- **PPO fine-tuning:** 60 000 steps, each step one prefix encode; bounded by the 14 PPO envs (≈ 1.6 h per k with
  3 seeds incl. CQL and evaluation). This does **not** speed up with more cores unless RC_ENVS is raised (section 9).
- x264 encodes are about 1.5× faster than x265 ones at these settings, so the x264 run takes somewhat less time.

## 6. Running on Slurm

All parallelism is `multiprocessing` on **one node**; the scripts can't span nodes. Request one full node per job.
Chain the steps with dependencies; because of the caching, a job that hits its wall time is simply resubmitted.

`tools/hpc_step.sbatch` (create it once; it works for either encoder):

```bash
#!/bin/bash
#SBATCH --nodes=1 --ntasks=1
#SBATCH --cpus-per-task=64
#SBATCH --mem=128G
#SBATCH --time=48:00:00
#SBATCH --output=%x-%j.out
# usage: RC_CODEC=x265|x264 RC_WORK=<dir> sbatch --export=ALL --job-name=<name> tools/hpc_step.sbatch <python args...>
# run it from the project folder of that encoder (section 7)
set -euo pipefail
source ~/.bashrc; mamba activate rc            # or: module load ...; source venv/bin/activate
export RC_WORKERS=$((SLURM_CPUS_PER_TASK - 2)) RC_ENVS=14
cd "$SLURM_SUBMIT_DIR"
echo "  $(date +%T) $RC_CODEC $* started" | tee -a $RC_WORK/$SLURM_JOB_NAME.log
python -W ignore "$@" 2>&1 | grep --line-buffered -v -i -E 'warning|batch_size|n_steps=' | tee -a $RC_WORK/$SLURM_JOB_NAME.log
echo "  $(date +%T) ALL DONE" | tee -a $RC_WORK/$SLURM_JOB_NAME.log
```

`tools/hpc_chain.sh` (submits steps 5–13c with dependencies; call it once per encoder):

```bash
#!/bin/bash
# usage (from that encoder's project folder): RC_CODEC=x265 RC_WORK=/scratch/$USER/rcwork bash tools/hpc_chain.sh
set -euo pipefail
dep=""
for s in rl_matrix seeds switch overshoot lagr expand extend expand2; do
  j=$(sbatch --parsable --export=ALL ${dep:+--dependency=afterok:$dep} --job-name=${RC_CODEC}_$s tools/hpc_step.sbatch experiments/$s.py)
  echo "$s -> job $j"; dep=$j
done
```

Steps 1–2, 11a–b and 13a–b (clip preparation and downloads) run first, interactively or on a transfer node; 11b and
13b need their downloads finished. Steps 3, 4 and 10 are independent of the chain and can run in parallel with it
(step 4 should finish before step 5 if you want `rl_matrix` to reuse its test search). Adjust partition/account
flags to the cluster.

## 7. The x264 run

The x264 run is the same pipeline in a second copy of the project folder (so its `results/` reports don't overwrite
the x265 ones) and a second work directory. It can run at the same time as the x265 run, on other nodes.

```bash
# a second project folder and work directory
rsync -a --exclude results/ ~/599project/ ~/599project_x264/ && mkdir -p ~/599project_x264/results
export RC_CODEC=x264 RC_WORK=/scratch/$USER/rcwork_x264
mkdir -p $RC_WORK
# reuse the x265 run's downloads (raw sources only; they are read-only after download)
ln -s /scratch/$USER/rcwork/src  $RC_WORK/src
ln -s /scratch/$USER/rcwork/more $RC_WORK/more
cd ~/599project_x264
```

Then steps 1–13c of section 5 in this folder, **skipping the downloads 11a and 13a** (the links above provide them).
Step 1 re-downloads only the 100 MB of pilot clips. The `--prep` steps rebuild `clips/`, `films/` and the clip-window
files from the same sources with the same deterministic rules, so both runs use identical clips. Check that the GOP
counts printed by `expand2.py` match the x265 run (section 8). Don't share `clips/` or `gops/` between the two
work directories: the scripts create files there on first use, and two runs at once could collide.

What is the same in both runs: clips, GOPs, splits, seeds, the STATIC pattern and action space, the scene-cut
detector (pixel histograms, no encoder), every hyperparameter. What differs: every encode, including the cheap
first-pass complexity features the policy sees (an ultrafast constant-QP pass made with the encoder under study), so
the constant-QP curves, the budgets, the search, the trained policies and the validation choices are each encoder's
own. Neither run ever calls the other encoder. The rows labelled with the encoder's own rate control use x264's ABR / 2-pass modes, with and without its default
AQ + mb-tree.

Report prose: `extend.py`, `expand2.py` and `codecs.py` name the encoder in use. The earlier reports (`rl_matrix`,
`seeds`, `switch`, `overshoot`, `lagr`, `cutspec`, `expand`, `static_pattern`, `rl_suggestions`) say "x265" in
their headings even in the x264 run; in `~/599project_x264/results/` read those as x264 (or fix them with
`sed -i 's/x265/x264/g' results/{rl_matrix,seeds,switch,overshoot,lagr,cutspec,expand,static_pattern,rl_suggestions}_report.md`).

**The side-by-side report**, once both `expand2.py` runs have finished (from the x265 project folder):

```bash
python experiments/codecs.py --x265 /scratch/$USER/rcwork --x264 /scratch/$USER/rcwork_x264
```

It writes `results/codecs_report.md`: for constant QP, each encoder's own rate control, the causal rule, the RL
policy at every k and the hindsight search, the saving vs the encoder's own constant QP ("own"), the saving vs x265
constant QP ("common", which includes the x264-vs-x265 codec gap), GOPs over budget, the share of the search's gain,
and paired 95 % CIs for: RL k=5 vs each encoder's best own rate control, search vs RL, RL gain in x264 vs in x265, and
the codec gap.

## 8. Sanity checks while it runs

- `tail -f $RC_WORK/<name>.log`: every finished stage prints `  [<stage>] <seconds>s`; scripts print `STAGE ... done`
  between phases.
- Data check (not a result): after `infos`, `expand2.py` prints the GOP counts per split. With the sources in
  section 5 they are `train 861, val 296, test 494` GOPs, in both runs. Different totals mean a download failed or a
  source changed: check `$RC_WORK/fetch_more.log` and `results/*_clips.json`.
- A stuck encoder is killed after 120 s and retried 3 times (`hm265.encode`); repeated timeouts mean the node is
  oversubscribed (lower RC_WORKERS).
- Out-of-memory while building CQL data at k = 29: keep `LOG_CAP = {29: 24}` or request more memory.

## 9. Bigger runs (after the baseline runs have finished)

Put every scale-up in its own work directory so it never mixes with the baseline runs, e.g.
`RC_WORK=/scratch/$USER/rcwork_big` with the `clips/`, `src/`, `more/` folders symlinked from the baseline run of the
same encoder. Apply a scale-up to both encoders if it is to appear in the codec comparison. Report each scale-up next to
the baseline numbers, not instead of them. In order of value per CPU-hour:

| Change | Where | What it buys | Cost |
|---|---|---|---|
| **More seeds** (3 → 5 or 10) | `SEEDS` in `expand2.py` | Tighter CIs on the k curve; settles which k is best | +1.6 h per k per 3 seeds at 14 envs |
| **Stronger search** (`n_eval` 300 → 1000, `search_seeds` 2 → 4) | `CFG` in `expand2.py` (and `rl_matrix.py` for the old training clips) | A better teacher for CQL and a tighter ceiling, so "share of search gain" is less inflated by a weak search. Report the share against both ceilings | ≈ 6× the search time; embarrassingly parallel |
| **Gain-vs-encodes curve** for the search | log the best PSNR after 50/100/…/1000 encodes in `hm265.hill_climb` | Shows whether the search had converged at 300 encodes | free if done with the stronger search |
| **More PPO** (`ppo_steps` 60k → 200k) and **more envs** (`RC_ENVS` 14 → 32–64) | `CFG`, env var | Matches training length to the larger data; tests whether longer lookaheads were undertrained | Changes the recipe: rerun k = 0, 5, 10, 29 as a block and compare paired |
| **No LOG_CAP** at k = 29 | `LOG_CAP = {}` | Removes the one RAM compromise in the k curve | needs a large-memory node; watch peak RSS |
| **More data** (UGC: all GOPs per clip instead of 8; more categories like Gaming, Animation, Lecture; more film windows) | `CFG["ugc_gops"]`, `UGC_CATS` + `fetch_more.sh`, `CFG["film_windows"]` | The learning-curve question: does the k curve keep improving with data? | Downloads need the user's approval; search cost grows linearly |
| **Fidelity** (B-frames, AQ/cutree on, 720p, VMAF) | `hm265.X265_ARGS` / `X264_ARGS`, `W, H` in `hm265.py` and `rcrl_data.py` | Answers the main threats to validity | Real code changes and every cache invalidated: treat as a new study, new `RC_WORK` |

Rules for scale-ups: keep the train/val/test split by source, select anything (k, rule p, recipe) on validation only,
and keep reporting the % of GOPs over budget next to the saving.
