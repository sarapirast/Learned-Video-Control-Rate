RL Rate Control Field Guide

What each policy in our project is, written for someone who knows supervised learning, CNNs, LSTMs and transformers, but not reinforcement learning. Every RL idea is tied back to the encoder problem we're solving.

RL in one page

In supervised learning you have inputs and correct labels, and you minimise a loss. Reinforcement learning is for problems where nobody can give you the correct label. You only find out how good a whole sequence of decisions was after you've made them.

Our problem fits that shape. We encode a GOP one frame at a time, choosing each frame's QP. Nobody knows the "correct" QP for frame 7. We only learn, after frame 30, how many bits the GOP used and how good it looks.

Why this is harder than supervised learning

  • Credit assignment. The reward arrives only after frame 30. If the GOP went over budget, the learner has to work out which of the 30 QP choices caused it, from many episodes.
  • The data depends on the policy. A supervised dataset is fixed. In RL the data comes from the policy's own behaviour, so changing the policy changes what it sees.
  • Data is expensive here. Every step is a real encode, so a training run gets about 2,000 episodes. Most RL successes use millions.

A loose analogy: an LSTM or transformer that emits a sequence of decisions, where the loss is computed only on the final outcome and never per token.

The hindsight search

The search is not RL and not a policy. It's a brute-force optimiser that cheats on purpose:

  • It knows the whole GOP in advance.
  • It starts from a fixed QP pattern and nudges one or more frames' QPs, keeping a change if the score doesn't get worse. That's hill-climbing.
  • Every candidate plan gets a real encode, about 600 per GOP and budget.

It has two jobs:

  1. Reference point: how good could we be with perfect knowledge? On v1 test it scores 9.09 (x264) and 9.62 (x265).
  2. Teacher: its logged plans, with their scores, are the training data for BC and offline RL.

The research question is how much of the search's score a real single-pass policy can capture, and whether lookahead helps.

Lookahead k

At frame t, a policy with lookahead k may also see the first-pass complexity and cut flags of frames t+1 … t+k. A real encoder gets this by buffering k frames, which adds k frames of delay. k = 0 is strictly causal; k = 29 sees the rest of the GOP.

The input size stays at 346 numbers whatever k is. Slots for frames the policy may not see are zeros, much like padding and masking in a transformer.

Methods run on v1

Pavneet's code implements about 18 methods. Three have been run on data v1, for both encoders, at k = 0, 2, 5, 10 and 29, with 3 seeds each.

Behavioural cloning (BC) run on v1

Plain supervised learning. Training pairs are "observation at frame t → the action the search chose at frame t", using only the best search plan per GOP and budget. The model is an MLP classifier over 7 classes, trained with cross-entropy, like an image classifier whose image is the observation and whose label is the QP offset. At test time it picks the most probable action.

Weakness

It copies what the search did but never learns why. Once it drifts from the search's plan, for example by overspending at frame 5, it reaches states the search never visited and doesn't know how to recover. This is called distribution shift or compounding error.

On v1

Overshoots the budget on 16–26% of test GOPs. It gains the most from lookahead, mainly because lookahead helps it avoid overspending.

CQL → PPO run on v1

Pavneet's core recipe, in three steps.

1. CQL (Conservative Q-Learning), offline RL. It learns from the fixed set of search plans, with no new encodes.

  • What it learns: Q(s, a), the expected final score. The policy is "pick the action with the highest Q".
  • How: through the Bellman equation, Q(s, a) ≈ reward + Q(next state, best next action). It's a regression whose target uses the network's own predictions, which spreads the end-of-GOP score back to earlier frames. That's how it handles credit assignment.
  • The fix CQL adds: with a fixed dataset, the network can wrongly give high Q to actions that never appear in the data, and the policy then picks exactly those. CQL penalises Q for actions not in the data: if you haven't seen it, don't trust it.
  • Advantage over BC: it uses all logged plans, good and bad, with their scores, so it learns what makes a plan good.

2. Distillation. The CQL result is copied into a policy network by training it to match a softmax over CQL's Q-values. That's supervised learning again, as in knowledge distillation.

3. PPO (Proximal Policy Optimisation), online fine-tuning. The policy now acts in the real encoder for 60,000 steps (about 2,000 GOPs). PPO is a policy-gradient, actor-critic method:

  • Actor: the policy network, observation → probabilities over the 7 actions. During training it samples actions, which is how it explores.
  • Critic: a second network that predicts V(s), the expected final score.
  • Update: compare each episode's actual score with what the critic expected. The difference is the advantage. Raise the probability of actions in better-than-expected episodes and lower it for worse ones, by gradient ascent on advantage × log-probability of the chosen action.
  • The "proximal" part: clipping stops any single update from moving the policy too far. Without it RL training often collapses. It plays a role similar to a KL penalty in LLM fine-tuning.

PPO is the same algorithm used in RLHF for LLMs, where the environment is a reward model that scores the LLM's text.

Why combine them

PPO from scratch would need far more than 2,000 episodes. CQL gives it a good start; PPO then fixes some of the offline policy's distribution-shift problems with real experience.

On v1

Overshoots on 14–37% of test GOPs. Before the penalty it saves more than any other method: 5.56% on x265 at k = 5.

Lagrangian PPO run on v1 · best so far

The same CQL → PPO pipeline, with a different reward:

reward = savings − λ × overshoot, with λ = 4

The idea comes from constrained optimisation (Lagrange multipliers): turn the hard rule "don't exceed the budget" into a price per unit of violation. λ = 4 is twice the price the final score uses, so the policy learns to be careful.

On v1

Score 4.67 (x264) and 4.12 (x265) at k = 0, about 66–75% of the search's gain, and over budget on only about 3% of GOPs.

Catch

It wins because it stays in budget, not because it saves the most. Lookahead adds at most about +0.6 for it.

What we're testing next

Each experiment answers a question raised by the v1 results.

A. Budget shield in progress

Not a new learner, but a safety layer wrapped around any trained policy:

  1. Before each frame, predict the GOP's total bits if we accept the policy's choice.
  2. If the prediction exceeds the budget, raise the QP until it fits, up to QP 51.

The prediction may only use what the policy is allowed to see, so the lookahead comparison stays fair. The closest analogue is constrained decoding in LLMs: tokens that would break the output format are masked at generation time, without retraining. In RL this is called shielding.

Question

BC and CQL → PPO save more than Lagrangian but overspend. If we stop them overspending, do they beat it?

Status

The smoke test on 10 val GOPs removed every overshoot, but the bit predictor was too pessimistic and fired when it didn't need to (score 2.44 → −2.40). Fixing the predictor comes next.

B. λ sweep and PID-Lagrangian queued

Train Lagrangian PPO at several prices (λ = 2, 4, 8) and with the PID controller at target violation rates of 1% and 5%. Plotting savings against violation rate gives a trade-off curve, a fairer comparison than one λ.

Each run also picks its best checkpoint on val, which is the RL version of early stopping. Training scores on v1 peak mid-training and then fall, so the final checkpoint is not the best one.

C. Model predictive control (MPC) queued

  1. Learn a model of the environment by supervised regression: frame features + QP → predicted bits and PSNR.
  2. At each frame, simulate many candidate QP sequences over the visible lookahead with that model, keep the best, and apply only the first frame's QP.
  3. Repeat at the next frame. This is receding-horizon planning.

The analogy is a chess engine or beam search: search over futures with a model, commit to one move, search again. It's the classic approach in rate control, and it uses lookahead explicitly, so it may show the effect of k more clearly.

D. Residual policy on a causal controller later · needs P2's estimator

Today the policy adds ±3 to a base QP that secretly comes from hindsight: the budget QP is the QP that exactly meets the budget. The fix is to use a simple, honest controller as the base, "budget per frame + complexity → QP", calibrated as frames are coded. The policy then learns only corrections to it.

It's the same idea as a residual connection in a ResNet: learn the difference from something that already works. It removes both validity problems found in the review (the oracle base QP and the budget leak), and the policy no longer has to learn rate control from scratch.

E. Decision Transformer or attention encoder later · new code

A Decision Transformer treats RL as sequence modelling. A GPT-style model reads (target score, state, action, state, action, …) and predicts the next action; asking for a high target score makes it act like a good plan. It trains offline on every logged plan, and the remaining budget can be an input token. Of everything here, it's the closest to models you already know.

An attention encoder over the visible lookahead frames, in place of one flat MLP over 346 numbers, gives the policy a natural way to use whatever k it's given.
